# Component review matrix

Use this lookup to turn “if it is a button, confirm…” into observable checks for a bounded task. [GUIDE.md](../GUIDE.md) remains authoritative; these rows apply its existing rules, not a separate standard or new rule IDs. Follow the existing [priority and emphasis hierarchy](../GUIDE.md#priority-hierarchy-and-conflicts).

## Select checks by role and consequence

1. Identify what the component does, which record or scope it affects, and what result the user needs. A card's appearance does not tell you whether it is a link, choice, action or static summary.
2. Combine relevant rows. An asynchronous Save button needs the button, save, pending-operation and feedback checks. A read-only preview does not acquire a save requirement. Use the [interface-pattern lookup](interface-patterns.md) for the surrounding workflow.
3. Inspect the rendered component, exercise applicable transitions, and compare its claims with the established product contract. Mark a check Pass or Fail only to the extent the available evidence establishes it. Source inspection can establish a defect, and a screenshot can establish a visible state; neither proves unexercised runtime behavior. State the evidence type and its limits, and leave the remaining runtime checks Pending.
4. Record expected and observed behavior in the existing [review record](../REVIEW_TEMPLATE.md#procedure-and-results): **Pass**, **Fail**, **Pending**, or **Not applicable with a reason**. Split mixed results; an operable button can pass keyboard checks while its save outcome remains Pending. Name the component, state, revision and environment; do not duplicate evidence in a second report.

For a shared component, reuse evidence for identical behavior and state combinations, but inspect consequential instances and meaningful differences in labels, handlers, scope, layout and permissions. A passing example does not establish that every consumer works. Prioritize harm, lost work, blocked tasks and misleading state before cosmetic findings; this adds no numerical grade or shipping verdict.

## Choose the test environment

Exercise failure, duplicate-activation and retry checks in an authorized disposable fixture or controlled test environment with known side effects. Before retrying, establish whether the original operation failed, completed or has an uncertain outcome; a timeout alone does not prove failure. Follow the application's contract for checking completion and preventing duplicate effects.

A review does not authorize new live mutations or intentional disruption. If a suitable test environment is unavailable, inspect handlers, safeguards and existing test evidence; report supported findings and leave unexercised runtime behavior Pending. Do not disable live dependencies or repeat consequential operations solely to complete this matrix.

## Common checks

Apply these to the affected controls and supported contexts; the component rows add specific questions.

- **Meaning:** The visible label and accessible name identify the same purpose. Necessary scope, units, prerequisites and consequences remain available. Use [practical language](../GUIDE.md#practical-interface-language); concision must not remove decision or recovery help.
- **Operation:** Use semantics appropriate to the role. Check supported keyboard and pointer/touch operation, focus order, visible focus, names, roles and states. An icon or color alone must not carry essential meaning. Follow [AUDHD-11](../GUIDE.md#audhd-11-keep-controls-readable-and-operable) and the [visual standard](../GUIDE.md#visual-standard), including actual contrast and target measurements.
- **Presentation and continuity:** Check relevant narrow/enlarged layouts and supported appearance/accessibility settings. Controls, labels, errors and destinations remain discoverable and usable. Appearance changes preserve drafts, request ownership, acknowledgments, record identity and filters; returning from appearance settings restores useful task context and focus. See [AUDHD-05](../GUIDE.md#audhd-05-preserve-focus-and-spatial-stability) and [AUDHD-10](../GUIDE.md#audhd-10-support-interruptions-and-working-preferences).

## Finish with the task outcome

Component checks complement the complete workflow; passing all rendered controls does not establish functional coverage. Follow [AUDHD-12](../GUIDE.md#audhd-12-validate-complete-tasks-and-report-actual-evidence) from entry to the intended outcome, including applicable failure, recovery and return. Use the existing [manual accessibility checks](manual-accessibility-checklist.md) when those checks are in scope; mark untested assistive technologies and participant understanding Pending.

Keep evidence proportional. For example, an inspection may establish that “Save permissions” has an appropriate label and state, while an exercised keyboard test establishes operation. A successful save response still does not verify allowed and denied access. Record those as distinct results against the same task rather than marking the entire button or interface Pass.

Automate repeatable regressions when useful, but retain manual checks of meaning, task comprehension and rendered relationships. Do not replace these with word-count limits, banned-word tests, screenshots alone or an aggregate completion score.

## Worked review example

**Illustrative completed record:** the observations below are invented to demonstrate recording mixed results, not executed evidence about this toolkit or a real application. Replace them with actual observations when reviewing a product.

**Task and context:** Save Mira's permissions in fictional build `demo-r1`, using a desktop browser, keyboard and disposable mock service. Combine the button, save, pending-operation, feedback and verification rows in one record. Saving stores configuration; effective access requires a separate check. The submitted snapshot is version 8; the user makes a newer edit while that request is pending.

| Action/check | Expected result | Observed result in this fictional example | Status and evidence |
|---|---|---|---|
| Identify the Save action | Label and nearby context identify the person, saved scope and separate verification step. | “Save permissions” appears in Mira's editor with the save destination and check requirement visible. | Pass for this rendered state — visual and semantic inspection; AUDHD-01, 04, 09. |
| Operate by keyboard | Reach and activate Save with visible focus and one request. | Keyboard activation submits once; focus remains in the editor. | Pass for this interaction — browser exercise; AUDHD-05, 11. |
| Persist the submitted snapshot | Acknowledgment and readback identify version 8, not the newer edit. | Mock service readback matches version 8; the newer draft remains in the editor. | Pass within the mock — request/readback evidence; AUDHD-06. Production persistence remains untested. |
| Interpret feedback after newer editing | Completion of version 8 still leaves the newer draft marked unsaved. | The interface says “Saved” without identifying the older version; the response handler clears the dirty flag regardless of later edits. | Fail — browser observation and source inspection; AUDHD-06, 07. The source finding can still be reported if runtime access is later unavailable. |
| Verify effective permissions | Check allowed and denied access for saved version 8. | No effective-access service is connected to the fixture. | Pending — outcome not exercised; AUDHD-12. Successful storage does not prove effective access. |

**Result:** Fix the misleading acknowledgment and repeat that transition check. Verify effective permissions in a suitable environment before claiming the task outcome. Narrow layout, assistive technologies and participant understanding are outside the exercised evidence and remain Pending; the component has no single overall Pass score.
