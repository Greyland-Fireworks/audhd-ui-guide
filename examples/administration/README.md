# Harbor Team Hub — Administration demo

A fictional workspace for the Harbor project team's notes, calendar, room bookings, tasks and requests. It uses canonical skins, the shared [control baseline](../../packages/audhd-ui-framework/controls.css) and native controls without a framework or build step. **Refreshing or closing the page resets this demo's records, drafts, saves, settings, export requests, activity and acknowledgments.** JSON note downloads create real files that can be imported as new copies; the workspace itself has no durable storage, shared server or real account administration. The account-role demonstration concerns note access only; it does not authorize the hub's calendar or work tasks.

From the repository root, serve the example with the existing development dependencies:

```sh
npx --no-install vite --host 127.0.0.1 --port 4187 --strictPort
```

Open `/examples/administration/`. Run its isolated browser checks with:

```sh
node examples/administration/check.mjs
node examples/administration/activity-check.mjs
node examples/administration/recovery-check.mjs
node examples/administration/notes-check.mjs
node examples/administration/notes-tools-check.mjs
node examples/administration/schedule-check.mjs
node examples/administration/work-check.mjs
```

Each browser check accepts the example URL as its first argument when using another port. Use an isolated preview server; the notes checks also exercise temporary JSON files. Run the model assertions separately with `node examples/administration/notes-state-check.mjs`.

## Try the tasks

1. Open **Calendar & rooms**. Compare meeting start times, durations and overlaps on the week calendar; use the month view to select a day or the agenda to read the same reservations as a list. Compare room schedules before creating a meeting. Test a conflicting room/time and use a suggested alternative; cancel a saved meeting and restore it only if its slot is still free.
2. Open **Tasks & requests → Tasks**. Compare the Blocked, Not started, In progress and Complete lanes, then switch to **Grouped list** without changing the records. Assign work, set its due date and link a related note, meeting or request. Try completing a task before its prerequisite; correct the dependency or finish the prerequisite. Reopen completed work by changing Progress and saving.
3. Open **Tasks & requests → Requests**. Follow Draft → Submitted → Decision for an equipment or workspace request. Return a submitted version with a reason, correct the draft and submit again; changing a newer draft cannot silently alter an earlier submission. Approving the replacement cable request leaves the linked room-display task blocked until its progress is explicitly changed.
4. Open **Notes**. Eight active notes are already listed across three notebooks; two more notes are archived and two are in Trash. Browse a notebook or create a note, then edit its title, body or notebook. Visit **Appearance** and return before saving to inspect draft retention.
5. Save a note, make a newer draft and open **Saved versions**. Restoring a version prepares a draft; it asks before replacing unsaved work and does not replace the saved note until Save. Archive a note, move one to Trash and restore it to active notes.
6. Open **Administration → Workspace settings**. The default notebook preselects a location for new notes. Compare the proposed body-length limit with actual saved note lengths before saving; lowering it retains existing text. **Notes → Notebooks** lets you create a notebook or edit its name and description.
7. Open **Administration → Note transfers → Import & export notes**. Download the saved notes as JSON, choose that file and review the preview before **Import copies**. Existing notes and drafts remain unchanged. Imported copies start their own history at version 1.
8. Open **Administration → Users & access**. Mira and Sam are listed with their saved note roles, check status and next action. Change Mira's role, enter a reason, Save and **Check saved access**. A newer role draft remains separate from the checked saved version; resetting Mira's draft leaves Sam's draft intact.
9. Open **Administration → Activity & logs → All events** to inspect actions from this session. **Warnings** is the first task and includes errors. **Example history** offers a separate labeled sample for exploring warnings, unknown entries and longer pagination.

To explore implementation choices or injected failures, turn on **Guide notes**. It starts off. Local **Why this design** disclosures link to the guide; ordinary decision help stays available independently. The capability examples at `#settings` are teaching material, reachable through Guide notes and **All pages**, rather than a competing main administration task.

## Navigation and local help

[app.js](app.js) keeps one destination registry for primary navigation, secondary tasks, breadcrumbs and **All pages**. The seven main destinations are **Overview**, **Calendar & rooms**, **Tasks & requests**, **Notes**, **Administration**, **All pages** and **Appearance**, with Appearance last and adjacent to the other entries. Notes contains **New note**, **Notebooks**, **Archived notes** and **Trash**. Calendar & rooms contains **Week calendar**, **Month calendar**, **Meeting agenda**, **Room availability** and **New meeting**; Tasks & requests separates **Tasks** and **Requests**.

Administration groups **Users & access**, **Workspace settings**, **Note transfers** and **Activity & logs**. Note transfers contains real JSON note transfer (`#transfer`), the separate request-recovery simulation (`#recovery`) and its **Request limits** (`#settings/requests`). Activity & logs contains **Warnings** and **All events**. Record destinations derive from current people, notebooks, notes, meetings, tasks and requests; stable IDs preserve links across renames and moves.

**Harbor Team Hub** is the linked breadcrumb home on every page and opens Overview. At home it is the only breadcrumb; other pages follow it, with linked parent destinations and the current page identified. Breadcrumb navigation uses the same draft, filter, history and focus behavior as other task links.

The directory lists parents with alphabetized sibling destinations without a query, including each note's **Saved versions** and teaching destinations; its optional filter retains matching ancestors and is retained on return. Navigation automatically expands the current branch instead of accumulating every previously visited branch; explicit open/closed choices are retained. On narrow screens, **Sections** opens the complete menu. Selecting a destination closes it; Escape returns focus to the toggle.

Overview combines a compact timeline and a named next-meeting summary with **Problems to resolve** and **Ready to continue** links. The meeting summary states its date, duration and room; the timeline frames today's meetings rather than filling the first screen with empty hours. Work summaries name the owner or requester where relevant. **Administration review** keeps unchecked roles and ordinary administrative drafts below the coordination work, while actual administrative problems still appear in Problems to resolve. These regions do not embed editors or a routine activity feed. **Users & access** keeps each saved role, reading/editing consequences, check evidence and direct actions inside one account card. The neutral **Users & access** badge counts all configured accounts. The **Overview** badge combines observed problems across the hub, including blocked tasks, returned requests, invalid submissions, unavailable checks, and rejected or uncertain export requests. Calendar & rooms and Tasks & requests also show their own problem counts. Warning badges use warning color, a striped edge, a warning symbol and a double border; their accessible names describe the count. Each affected account counts once, regardless of filtering or multiple issues. Routine drafts and unchecked roles remain review work without raising that warning. Note transfers retains its unfinished-task count. Historical activity does not inflate current-task counts. **Configured accounts** means accounts with saved demo roles, not signed-in users or pending activations.

An unchecked role is labeled **Review**, an unavailable check **Warning**, and an invalid save **Error**. Missing evidence does not establish a permission failure or security threat. **Check saved access** reveals and focuses the owning check control; it does not save a draft. A successful check clears that review item, while any newer draft remains outstanding. Saving a new role invalidates the earlier check.

Open **Administration → Note transfers → Request limits** for the [numeric-control pattern](request-settings.js). Capacity and timing jointly define one fictional export-request policy and share a visual group. Essential timing and unit semantics stay beside the controls; local information help explains when to use a limit, when to leave it off and concrete effects of the two values. That help stays inside the fieldset, independently of Guide notes. Demonstration defaults and accepted ranges are not production recommendations.

The quantity and unit are both editable inputs: choosing a different unit intentionally proposes a different duration and the preview spells it out before Save. This is distinct from a display-unit preference that should preserve the underlying duration. Decimal values are converted exactly to whole milliseconds, without silently rounding an unsupported value. For example, `0.017` minutes saves as `1,020` milliseconds. Blank or sub-millisecond input produces a field-associated error and focuses that input; turning the policy off retains the unfinished numbers. The policy does not limit the demo's export requests or control a real service.

## Calendar, tasks and requests

[schedule.js](schedule.js) shows week calendars with meeting blocks positioned by start time and sized by duration. Overlapping meetings use separate columns; short or crowded blocks expose a full-text preview on pointer hover or keyboard focus without stretching the displayed duration. The month grid shows daily reservations; selecting a day reveals its full list. A meeting agenda provides a list alternative. Narrow week views show one selected day with Previous/Next day controls, preserving readable times instead of compressing seven columns. The time zone and current-time marker identify the time context. New meetings start on the selected calendar date. If an existing draft belongs to another date, the user explicitly keeps it or starts a new one.

Room availability compares three rooms on one time scale, with a compact availability summary and each room's decision and booking action before its plot. Filled reservations and a dashed proposed interval distinguish booked time from a choice that has not been saved. On narrow screens, all three room timelines stack vertically with the same time range and scale; capacity, equipment and booking actions stay with each room. The rooms hold 4, 8 or 12 people and have different equipment. Single-occurrence bookings use the device time zone, a same-day interval between 08:00 and 18:00, and a duration of 15 minutes to 8 hours. Save checks capacity, equipment and overlapping reservations together. Suggested alternatives preserve the meeting draft and disappear when a changed proposal makes their earlier check stale. Cancellation releases the slot, and restoration checks availability again. No invitations are sent or real rooms reserved.

A saved meeting opens with its date, duration, room and purpose before the editing form. **Open notes**, **Create follow-up task** and **Change reservation** stay with those saved facts. Editing shows the proposed duration and a changed-only **Saved / Proposed** comparison beside Save. Newer drafts never replace the saved summary or its note link; unchanged reservations cannot be saved again. Discard restores the saved values and clears the comparison.

[work.js](work.js) places five seeded tasks in **Blocked**, **Not started**, **In progress** and **Complete** lanes with filtered counts. Compact cards align owner, due date and next action, and show named prerequisites and related requests. **Grouped list** offers the same records and actions without a board; neither view requires dragging. Filters, drafts and the chosen view survive task navigation. Blocked work requires a reason; circular dependencies and completion before prerequisites are rejected. A task may link a meeting, note and request. The room-display task explicitly links the replacement-cable request; approval never automatically unblocks or completes that task.

Four seeded requests demonstrate a draft, pending review, approval and return for correction. **Draft → Submitted → Decision** identifies the current stage, with returned reasons and correction links visible. The editable draft and saved candidate are separate from the immutable submitted snapshot. Later unsaved or saved edits remain identified while the review applies only to the submitted version; an older approval never labels a newer draft approved. Submission history retains earlier decisions and their submitted details. Saving a correction does not submit it; resubmission is an explicit action. This is a local workflow demonstration, with no purchasing service, notifications or reviewer authorization.

These modules own their visit-memory drafts independently of navigation. Overview links unfinished work and observed problems to the relevant record or field. The seeded blocked task and returned request contribute two problems; a routine draft or an unchecked note role does not itself mean something failed. Activity entries describe supported actions from this visit. A successful simulated save does not establish shared-server persistence or concurrent-user protection.

## Notes, history and files

[notes-state.js](notes-state.js) owns saved notes, independent drafts and saved content versions. [notes.js](notes.js) renders notebook cards with counts and previews, editing, saved-version comparison, Archive and Trash. Dated version choices and a line-by-line comparison keep the selected version beside the current saved version and identify changed fields; neither is confused with an unsaved draft. Moving a note does not save or discard its draft or erase history. Archived and trashed notes remain readable, with their restoration action before the content; restore them to active notes before editing. There is no permanent-delete action. Restoring an old content version creates an unsaved draft, with a scoped confirmation if that would replace existing edits. Notebook creation appears before the existing notebook editors; named disclosures keep each editor available without presenting every form at once. Direct control links open the relevant disclosure before placing focus.

[notes-tools.js](notes-tools.js) provides notebook editing, workspace settings and JSON transfer. The default notebook changes the initial choice for new notes; it does not move existing notes. A visual impact preview compares actual saved note lengths with the proposed maximum and identifies affected notes before Save. The saved body-length limit applies to future note saves and imports. Lowering it never truncates stored text or drafts; an over-limit note must be shortened or the limit raised before its next save. These settings affect the practice workspace, unlike the separate simulated request-limit example.

A JSON download contains saved notebooks, note content, status and history. It excludes unsaved drafts, meetings, tasks, requests, workspace settings, account roles and activity. The interface reports a requested browser download, without claiming which folder received it. Both import and download support files up to 10 MB; oversized downloads are refused without truncating history. Import accepts the version 1 Shared Notes format, subject to the current body-length limit. Previewing changes nothing. Import creates new IDs and notebook copies, suffixes conflicting notebook names and starts each copied note at version 1; exported earlier history is not restored into those copies. Validation runs again before copying so a changed limit cannot bypass the check. A rejected file leaves existing records and drafts unchanged.

## Interrupted-request recovery

The separate **Administration → Note transfers → Request a notes export** [simulation](recovery.js) starts with normal acceptance and confirmation. It creates an accepted-request record, not a file; actual downloads belong to **Import & export notes**. To exercise recovery, turn on **Guide notes**, open **Try recovery paths** and then:

1. Select **Service accepts, but response is lost** and request an export. The simulated service creates an accepted-request record before the response fails. The screen reports an unknown outcome and retains the submitted name and request ID.
2. Edit the name to create a newer draft, navigate away and return, then choose **Check whether this request was accepted**. This reads the existing request and offers confirmation without creating a second request.
3. Choose **Request accepted; confirmation unavailable** and confirm. The accepted request remains. Select **Response and confirmation available**, retry confirmation and inspect the unchanged accepted-record count. **Restore simulated service** also remains available for an active failure with Guide notes off.
4. Use **Connection fails before acceptance** or **Service rejects before acceptance** to distinguish absence/rejection from an unknown result. A retry keeps the original ID and submitted name. Starting a different request requires an explicit action and uses the retained newer draft.

The service's accepted-request map and browser state intentionally share this demonstration's memory. Its controlled asynchronous boundary demonstrates response loss, reconciliation, duplicate protection and a separate confirmation that the accepted name matches the submitted snapshot. It does not generate or verify an export file, test an HTTP transport, or establish cross-process durability. A production adapter may reuse an ID only when the supported service contract guarantees deduplication. Without that contract, reconcile through available records before permitting another mutation. Do not copy the simulated service as a security or persistence boundary.

The [recovery browser check](recovery-check.mjs) exercises the visible recovery path and inspects creation counts, submitted identity, newer drafts and late responses. An API-only retry with a manually supplied old identifier would not establish that the interface preserved the recovery path. See the dated evidence below for execution status.

## Activity review

**Activity & logs** opens **Warnings** first, with **All events** second. [activity.js](activity.js) presents timestamps, severity, plain-language descriptions and attention state in a table. The default **This visit** source reflects supported actions in the demo. **Example history** is a separate, visibly labeled historical sample; it does not describe the current people or exports. Unknown entries retain original text without an invented interpretation.

Counts cover the selected source, including new arrivals outside the loaded row snapshot, rather than only the current page. The arrival notice explains that difference. Acknowledgment removes an event from the unacknowledged count and reduces emphasis, while preserving severity, original detail and history; it does not resolve the cause. Acknowledgment belongs to this viewer's memory and resets with the demo.

The displayed event snapshot stays stable while being read. New events wait behind **Show N new events** instead of moving rows or focus. Users choose the page size, and each source/view retains its place during navigation. Events with an available remedy link directly to the relevant task or known control. Narrow rows put the event description before aligned timestamp/severity details and recovery actions. The [activity check](activity-check.mjs) covers the intended source, snapshot, acknowledgment and pagination behavior; these are simulated application events, not a production log connection.

## What to adapt

The [capability-state guidance](../../references/interface-patterns.md#capability-states-and-next-actions) describes useful distinctions, not a required status schema. A real product should name its actual dependencies and permitted next actions. Missing credentials need not prevent configuration; an implemented read-only verification should check the saved operation's identity or version, and stop with a useful result when it cannot establish the outcome.

Keep the existing product's persistence and authorization contracts. This example's workspace stays in memory and its permission checks are deliberately simulated. JSON transfer reads and writes local files through browser controls, while the separate request simulation exercises a controlled asynchronous boundary. Neither establishes production durability, general concurrency correctness or authorization. Use the [configuration contract](../../packages/audhd-ui-framework/CONFIGURATION.md) for source coverage and task-specific runtime verification, and the [recording-review example](../recording-review/README.md) for asynchronous recording review.

## Overview and control links

Overview is the default entry. Note drafts and validation problems link back to the relevant note. Account errors link to the reason field, unsaved account records to role editing, and saved roles awaiting verification to the check button. The URL names the person and target; navigation reveals that control without mutating values. Filters, per-record drafts and verification results survive route and appearance changes. Permission verification is tied to a saved version; saving again invalidates it. Workspace state remains fictional and in memory.

Activating the check moves focus to its result heading in the same panel. A fresh receipt distinguishes repeat checks with identical permissions. Completion feedback describes the saved role only; it never claims that a newer draft has passed or silently saves that draft.

Inline comments explain these state owners, version boundaries, non-mutating retries, focus fallback and token-only appearance updates. The recording adapters and unlock editor document their distinct persistence and navigation contracts beside the relevant code.
