# Configuration dashboard integration contract

Apply this contract when building a dashboard for an application's backend configuration, whether using the skill alone or integrating the optional framework. Repository analysis and source-backed coverage checks are part of the work without a separate prompt. Their presentation is proportional: reuse existing schemas, tests or maintained records when sufficient; create a separate inventory, map or reference page when requested or when it materially aids understanding, traceability or maintenance. Working, understandable workflows take precedence over elaborate supporting artifacts. The host application owns configuration semantics and persistence; the package's preference utilities do not discover or validate arbitrary backend settings.

## Preserve functional scope

Establish the user goals and observable completion outcomes alongside option accounting. Configuring a data source, declaring desired state, inspecting existing records and managing those records are distinct capabilities. When a requested administration task needs existing records or effective permissions, provisioning fields alone do not complete it. Use the application's supported administrative APIs or commands within authorization; do not infer permission to manipulate databases directly or add unrelated management features. Reconcile declared configuration with observed state where the task requires it, including changes that removing a declaration does not undo. Reuse compact coverage records rather than introducing another mandatory report.

Derive coverage from the requested user tasks and the application's discovered capabilities, not from a target number of controls or the easiest options to implement. Distinguish discoverability from support: putting a control in an advanced section preserves capability; listing an unsupported option in a reference does not. Do not redefine a broad dashboard request as a small demonstration merely because the runtime is local or the interface should feel simple.

For material exclusions, identify the affected task and a concrete reason grounded in user scope, permissions, application behavior or an environment constraint. A constraint on deployment or credentials does not automatically exclude unrelated workflows. “Advanced,” “outside this editor” and “not yet tested” alone are not reasons to remove requested capability. Treat implementation or verification gaps as unfinished work, with their impact and dependency stated. Continue supported work; resolve an actual scope decision with the user only when it cannot be established from the request and evidence. Do not silently turn a proposed reduction into the completion boundary.

Make material coverage limits visible before users depend on unsupported workflows. Explain externally managed settings, intentional exclusions and incomplete support separately, with the applicable reason and an established next step where available. Documentation completeness and a successful sample operation do not establish functional completeness.

## Discover configuration sources automatically

Discover all configuration sources for the target application within the authorized repository and available runtime context; do not require a configuration-file path from the user. Treat a supplied file as a discovery seed unless the user explicitly limits the scope to it. Follow application entry points, startup commands, configuration loaders, include/import chains, environment selection and deployment definitions. Search supported formats and code-defined defaults rather than assuming configuration is JSON or that every matching file is loaded.

Maintain a source register listing each discovered file or non-file source, its purpose, loader/consumer evidence and selection conditions. Distinguish live application configuration from examples, templates, test fixtures, generated copies, migrations and historical files. Include environment variables, command-line flags, database or remote settings when the application uses them. Record known external paths or sources that cannot be inspected and the resulting coverage limits; do not claim complete runtime discovery from repository inspection alone.

## Trace and account for every option

Reconcile discovered configuration with loaders, schemas, defaults, consumers, validators, overrides, write paths and tests. Include supported options absent from sample files within the requested scope. Follow nested objects, array entries and dynamically registered options; record the discovery boundary when runtime registration or unavailable code prevents complete enumeration. Do not infer behavior from names or sample values.

Record lifecycle and runtime applicability separately. Lifecycle can be supported, explicitly deprecated (still accepted), removed/ignored or unresolved, with evidence and a replacement when established. Runtime applicability can be effective, overridden, conditional/inactive, not loaded or unknown for the inspected environment. A deprecated option may still be active; an overridden or currently inactive option is not necessarily obsolete. Missing search matches alone do not prove a setting unused, especially with dynamic lookups or plugins. Distinguish source-established behavior from observed runtime use and leave unverified runtime status unknown. Discovery does not authorize deleting or migrating deprecated settings.

Verify source revision and runtime version before claiming a compatibility mismatch. An untested option is not necessarily newer, obsolete or unsupported. Label startup snapshots, health checks and direct observations according to what they actually establish; do not present a successful startup as per-option behavior verification.

Record source-declared, runtime-recognized, platform-applicable, editable and behavior-verified status distinctly. A flag listed in runtime help is not proof that the current platform or configured dependencies can use it. Explain known constraints before editing, disable unavailable actions with a reason, and identify unresolved applicability honestly rather than deferring a known rejection until Save or Apply.

Retain the following coverage information for each option in scope. Use a compact inventory or links to existing authoritative records; the table describes information to establish, not mandatory duplicate columns or a new document. Share common evidence and explicitly mark unresolved or inapplicable items. Do not drop option accounting merely because no separate inventory is delivered.

| Field | Required information |
|---|---|
| Identity and evidence | Exact configuration path, owning system, source file and symbol or line references for reads, validation and writes; unresolved links explicitly marked |
| Locations and provenance | All discovered files containing the setting, with key paths and line/symbol references; distinguish declarations/defaults, examples, loaded values, overrides and write destinations. Name non-file sources explicitly and identify the effective source when established. |
| Lifecycle and applicability | Supported/deprecated/removed or unresolved status, separately from runtime applicability; evidence, inspected environment, replacement if established and uncertainty |
| Meaning and constraints | Purpose, type, units, allowed values, validation and behavior for missing, null or invalid values |
| Decision guidance | Plain-language meaning of unfamiliar concepts, when the setting is useful or can remain unchanged, prerequisites and choice tradeoffs; evidence for recommendations and any unresolved meaning |
| Resolution and effects | Defaults, override precedence, dependencies, consumers, when a change takes effect and any apply/reload/restart requirement |
| Persistence | Save mechanism and scope, acknowledgment/failure behavior, permissions and sensitive-value handling |
| Dashboard coverage | User-facing name, owning task, editable control and navigable location, read-only presentation with reason, justified exclusion and affected task, or unfinished support and what it blocks |
| Verification | Relevant check and observed result, or Pending with the missing evidence |

Use shared references for common rules rather than repeating them. Represent repeated array/object fields with explicit path patterns and their instantiation rules; do not collapse independently meaningful settings into an opaque parent entry. Keep secret values out of inventories, charts and examples.

## Use a system map when it adds value

Use a map when requested or when dependencies, overrides or cross-system effects are difficult to understand in concise text or a table. Otherwise retain those relationships in the coverage record and contextual explanations without creating a diagram. When a map is useful, prefer Mermaid in a Markdown reference unless the host or requested format calls for another representation. Begin with meaningful systems: their user-facing purpose, relevant inputs and outputs, and established dependencies. Explain how configuration changes affect those relationships, including overrides and save/apply/restart paths where useful. Group by task or subsystem rather than source order or fixed batches of keys. Repeating the same declaration-to-loader path for every option is an index, not a sufficient system map. Mark unresolved relationships explicitly; do not draw speculative relationships as facts.

For a large map, use an overview and linked per-system detail where needed. Maintain exhaustive option accounting in the coverage record, mapping every entry to its owning system and known consumers, including read-only, excluded and unresolved options. A diagram may group options when individual nodes add no useful relationship; give individual settings nodes when their dependencies or effects clarify a decision. Use stable identifiers to connect system nodes, coverage entries and control locations, with human-readable labels and technical paths where needed. Supply a textual explanation of diagram relationships; neither a bare option table nor an overview alone establishes complete coverage.

Check Mermaid syntax with an available renderer and inspect the resulting diagrams for readable labels and relationships. Also follow the dashboard's actual map link: users must receive a readable rendered diagram and accessible textual explanation, not raw Markdown or Mermaid code presented as a finished map. Keep source downloads separately labeled. A render saved elsewhere does not verify the linked experience. If rendering is unavailable, deliver the source and textual explanation, identify the limitation and mark rendering verification Pending. Update the map and inventory when implementation reveals new behavior.

## Teach the program through the interface

Use meaningful primary task domains and named secondary workflows where complexity warrants them. Put common decisions and prerequisite status before expert configuration; do not use field order or generic “More settings” groups as the sole hierarchy. Follow the Guide's [navigation and responsive requirements](../../GUIDE.md#keep-navigation-levels-distinct), including routes from change/error summaries to affected controls and preservation of parent/child context. A simple dashboard may remain a single page.

Organize controls around user tasks while making the underlying systems understandable. Explain each system's purpose, relevant inputs and outputs, connections to other systems, and the consequences of changing its settings. Put essential dependencies and effects beside the affected controls. Explain why an option is inactive or overridden and distinguish the draft, saved value and effective runtime value where they differ.

Use plain-language labels and contextual help grounded in the traced behavior. Follow [AUDHD-09's decision guidance](../../GUIDE.md#audhd-09-put-essential-explanations-beside-the-decision): explain unfamiliar concepts, why and when they matter, and how to choose a value or leave the setting unchanged. Identify separate tools or setup needed for a feature to be useful; enabling an integration does not establish that its dependencies are installed, connected or working. Keep exact keys and the full map in discoverable technical reference material when useful; understanding ordinary operation must not require reading source code or a Mermaid diagram. Keep necessary consequences visible when optional detail is collapsed.

Provide the explanation each setting needs, using concise adjacent wording when sufficient and an accessible contextual disclosure when further detail is useful. Do not create a separate help control merely to repeat clear text. Lead with meaning and choice guidance; keep provenance available in contextual detail or a shared technical reference where useful, including file/key paths, applicable overrides and save destinations. Retain precise source evidence in the coverage record without requiring every user to read it. A disclosure containing only provenance and restart instructions does not explain an unfamiliar setting. Use navigable references where the host supports them and readable/copyable references otherwise. Identify non-file settings honestly. Explain consequential deprecation, inactivity or overrides beside the control; keep longer source details optional. Support keyboard and touch access, not hover alone, and never expose secret values through provenance details.

Separate [capability states and next actions](../../references/interface-patterns.md#capability-states-and-next-actions) in the existing coverage evidence and interface where relevant. A missing service, an environment restriction, an implementation gap and pending verification are not interchangeable exclusion reasons. Missing credentials may prevent verification while still allowing configuration. Put each dependency's consequence beside every affected task; do not rely on a warning under an unrelated setting.

For record administration, connect selection, inspection and actions to the same record and preserve useful return context. The [administration example](../../examples/administration/README.md) demonstrates this alongside field-linked errors and non-mutating verification retries. Its simulation is not permission to add unrelated management features or bypass supported administration interfaces.

## Connect references to controls

When reference material is exposed in the interface, use consistent user-facing names in it and the controls. Where search is needed, match visible labels, exact keys and relevant established terminology; a short reference need not introduce a search feature. Provide a working route from each editable entry to its control and from control help to the relevant reference. Navigation must reveal the destination, place keyboard focus meaningfully and preserve drafts; returning should retain any reference query and useful context. Do not offer an editing route for unavailable controls; explain the reason and any established alternative instead.

## Verify coverage and operation

Verify each requested task against its intended outcome: a setting persists and takes effect; a permission change produces the intended allowed and denied access; a delivery configuration reaches its intended destination. Startup health and a generic round trip establish only their tested path. When dependencies or authorization prevent a task-specific check, report that task's verification as Pending instead of claiming the feature works. Check both source coverage and user-task coverage; neither substitutes for the other.

Reconcile discovered sources and options, coverage evidence and dashboard dispositions, plus any delivered reference or diagram. Check that source references resolve and that effective/deprecated claims have evidence. Every option in scope needs an explicit disposition; an unresolved entry is an acknowledged gap, not completed support. Verify editable controls against the real read/write path, including validation, override and dependency behavior, effective timing, save failures and preservation of unrelated or unknown fields. Verify read-only and excluded settings cannot be changed through unintended controls. Preserve permissions and existing domain behavior.

Report coverage gaps separately from runtime checks. A complete chart does not establish working persistence, and a working save does not establish that every option is covered or that users understand the systems. Record unavailable checks as Pending; do not claim end-to-end completion while required integration remains unresolved.

Review coverage against the original requested tasks, not only the implemented allowlist. Check exclusions individually for a valid reason. Where reference search, navigation or maps are provided, exercise visible-label and exact-key search, reference-to-control navigation and return, draft preservation, keyboard focus and the actual rendered map destination as applicable. Check whether map relationships explain the systems rather than merely increasing node coverage. An unnecessary artifact need not be created to satisfy its presentation checks; necessary functional and coverage checks remain in force. Report functional, reference-navigation, rendering and evidence gaps separately where they occur.

Inspect unfamiliar settings and their opened help without relying on knowledge gained from reading the implementation. Check whether the interface explains the concept, its relevance, choice tradeoffs and prerequisites sufficiently to make the basic decision. Record missing explanations separately from source-reference or runtime failures. An agent inspection can identify these gaps; it is not evidence of user comprehension.

## Operational overview

Apply the Guide’s [status-first overview](../../GUIDE.md#status-first-operational-overviews) and [practical language](../../GUIDE.md#practical-interface-language) requirements to configuration entry screens. Derive rows from the same option and task state as the editor: blockers, failed operations, drafts needing review, saved changes awaiting application or verification. Identify the affected scope and link to the specific control or verification action. A saved configuration is not evidence of effective behavior; show unavailable or stale runtime observations explicitly. Preserve necessary prerequisites and consequences beside controls. Keep coverage evidence compact; this requires no new report format.
